In PICO OS 6, the spatial container (Spatial Container) is the core component used to host and manage spatial app content. You can place various types of content inside it, such as traditional 2D interfaces, 3D models, and a wide range of interactive components. Different spatial containers have distinct characteristics in terms of presentation and interaction capabilities. You can select the most suitable container based on the use case, enabling users to interact with content in the most natural and intuitive way.
## Spatial containers
Spatial containers are divided into two main categories: WindowContainer and Stage.
### WindowContainer
WindowContainer is the basic hosting container for apps, featuring a clearly defined spatial boundary. The content within the boundary is defined and controlled by the app itself, while any content beyond the boundary is automatically clipped. In general, when a user opens a WindowContainer, the container will by default appear at a position approximately **2.5 meters** in front of the user. Its center position always aligns with the current orientation of the user's HMD; in other words, wherever the user's head is oriented, the center of the WindowContainer will appear in that direction.
WindowContainer has two types: Planar, which primarily displays 2D content, and Volumetric, which primarily displays 3D content. An app can flexibly open one or more WindowContainers as needed.

* **Planar**
   Planar is a WindowContainer with limited thickness, similar to a "flat panel". It is mainly used to host traditional 2D interfaces commonly found in Android development, and can also be used to display smaller 3D objects.
   To design and develop UI for traditional 2D apps, or to port existing mobile or desktop apps to PICO OS 6, Planar is the ideal starting point. Planar continues the Jetpack Compose development paradigm and integrates PICO OS 6's spatial UI components (Spatial UI), enabling classic 2D apps to become spatialized. You only need to focus on the interface and functionality itself, while complex spatial interaction logic and window management are handled uniformly by PICO OS 6, greatly reducing repetitive work.
   ![Image](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/6932033fe57041f9ab803ef9ecc0f5b1~tplv-goo7wpa0wc-image.image)
* **Volumetric**
   Volumetric is another container that presents content in the form of a window, which can be understood as a "rectangular cuboid" with dynamically adjustable dimensions. Compared to Planar containers with limited thickness, Volumetric occupies a larger spatial volume and can accommodate larger 3D objects, thereby maximizing the user's 3D interaction experience within a limited area.
   Volumetric is mainly used to integrate 2D and 3D content, supporting basic 3D object display and interactive operations.
   ![Image](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/d7adf01799564d37b3f3767a62f939d9~tplv-goo7wpa0wc-image.image)

Caution: If 3D content exceeds the boundaries of the WindowContainer, it will be clipped. Therefore, to place larger 3D models, it is recommended to use Stage.
### Stage
Stage can be regarded as a space without boundary restrictions and supports placing more content, including UI components, 2D layouts, and 3D models.
To place large-scale content in the space or gain greater control over the environment, use Stage. Each time Stage is opened, spatial alignment is performed based on the user's HMD position and orientation: its center point is located at the user's feet, and the current spatial pose is used as the coordinate reference system, adopting a right-handed coordinate system, where the X axis points to the user's right, the Y axis points upward, and the Z axis points behind the user (opposite to the user's facing direction).
There are fewer layout restrictions for 3D and 2D content in Stage. You can also request higher-level interaction and perception permissions, such as gesture interaction, spatial anchor, and plane detection, to build immersive or mixed reality spatial scenes.

`Stage` provides multiple styles for controlling Video Seethrough (VST) of the real environment and the fusion method of virtual scenes, as well as image-based lighting (IBL) and rendering behavior of virtual entities. You can specify the style to use via the `openStage()` function's `style` parameter.
| **Style** | **Description** |
| --- | --- |
| Automatic | The Stage style is determined by the system. Currently, the system's default setting is the Mixed style. |
| Mixed | Virtual entities are always rendered, and image-based environmental lighting comes entirely from the real environment's Video Seethrough (VST). <br> The following figure shows a scene in Mixed style. Although the sky sphere uses the "Night Museum" map and enables image-based environmental lighting, the sphere still reflects the real environment's (bedroom) Video Seethrough (VST). | Progressive | Allows you to adjust the immersion level to change how the real environment's Video Seethrough (VST) blends with virtual entities. You can set the immersion level using the `Stage` parameter `immersion`. The immersion level ranges from 0 to 100: <br>  <br> * **immersion is 0**: The experience is similar to Mixed style, and you can still see the real environment. However, unlike the Mixed style, virtual entities are not rendered. Therefore, both the metal sphere and the Night Art Museum disappear. <br> * **immersion greater than 0 and less than 100**: As the `immersion` value increases, the rendering of the real environment gradually decreases, while virtual entities are rendered more prominently. <br> * **immersion equals 100**: Equivalent to the Full style. For details, refer to the description of the Full style. <br>  <br> The following image shows the scene with `immersion` set to 50 in Progressive style. In this example, a virtual metal sphere is enclosed by a sky sphere. The sky sphere uses the "Night Art Museum" map and enables image-based environmental lighting. You can see that the reflection effect of the metal sphere is a blend of the real environment (bedroom) Video Seethrough (VST) and the Night Art Museum. Specifically, the front of the metal sphere shows the real environment's Video Seethrough (VST), while the edges and back display the art museum. <br> ![Image](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/4c2e62feb1274952a37708921af99308~tplv-goo7wpa0wc-image.image) <br>  |
| Full | Virtual entities are always rendered, and image-based environmental lighting comes entirely from the virtual scene. Therefore, if you do not set a virtual scene, the application will display a pure black background due to the lack of lighting. <br> The following image shows the scene in Full style. ## Space state
The space where the spatial app resides has two states: Shared Space and Full Space.
| **Space state** | **Description** |
| --- | --- |
| Shared Space | In the Shared Space state, a space can be occupied by multiple applications simultaneously, supporting multi-application collaboration and content integration. <br> Shared Space only supports Planar WindowContainer and Volumetric WindowContainer. <br> ![Image](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/c4cd8d34ef24468db2c74ec2d1f4bcfd~tplv-goo7wpa0wc-image.image) |
| Full Space | In the Full Space state, a space is exclusively occupied by a single application. When an application opens a Stage, the system switches the space to Full Space state. At this point, the application fully occupies the current space, and windows of other applications are moved to the background. <br> In Full Space, the application occupying the space can place a Stage and multiple WindowContainers in the space simultaneously. After closing the Stage, the space automatically switches to Shared Space state. <br> Full Space supports the Stage, Planar WindowContainer, and Volumetric WindowContainer of the same application. <br> ![Image](https://p9-arcosite.byteimg.com/tos-cn-i-goo7wpa0wc/78cd54c2374e4e7dafefc42b4e43363e~tplv-goo7wpa0wc-image.image) |
The space state automatically switches as spatial containers are opened and closed. Assuming the initial space state is Shared Space, the state transition rules are as follows:

* When the app opens a Planar WindowContainer or Volumetric WindowContainer, the space state remains Shared Space. At this time, multiple apps can run simultaneously in the current space.
* When the app opens Stage, the space state switches to Full Space. At this point, the application fully occupies the current space. If multiple applications are running in the space simultaneously, the windows of other applications will be hidden in the background.
* After Stage is closed, the space state switches back to Shared Space, allowing multiple applications to run concurrently in the current space.

PICO OS 6 dynamically adopts targeted performance optimization strategies based on different space states:

* In the Shared Space state, the system deeply optimizes the rendering hierarchy for multitasking scenarios. Through mechanisms such as task priority scheduling, dynamic resource allocation, and layer composition optimization, even when multiple applications run simultaneously, it ensures smooth visuals and responsive operations, guaranteeing the user experience in a multi-window environment.
* In the Full Space state, the system further enhances rendering performance, focusing on global lighting, material detail, and interaction latency control. Even in highly complex 3D scenes, it delivers a high-fidelity, low-latency, stable, and reliable immersive experience.
